## 🔴 BLOCKER — `snapshot_rotates_to_keep_limit` fails deterministically; durability bug behind it

`cargo test` aborts the lib target at **202 passed / 1 failed**, so cargo never runs the
16 integration-test binaries. Fails 3/3 — not flaky.

**Root cause (real bug, not just a bad test):** `store::rotate_backups()` (`src/store.rs:428`)
keeps the newest `BACKUP_KEEP=10` snapshots **sorted by mtime alone** (`store.rs:456`).
`snapshot()` stamps backup names at **second granularity** (`store.rs:416`,
`%Y-%m-%d-%H%M%S`). When multiple `.bak*` files share one mtime tick — coarse FS
granularity (this WSL2 mount) or rapid successive snapshots — the tie-break is
`read_dir` order, which is mtime-blind. The freshly-written snapshot can sort into the
delete bucket, so **rotation deletes the snapshot it just created.** The test's
`assert!(new_bak.exists())` (`store.rs:539`) is what trips.

**Why it matters now:** this is the graph durability layer (GRAPH-DURABILITY.md §4 Layer 1),
and **Ph52 auto-compaction** (shipped this week) triggers back-to-back snapshots — exactly
the mtime-collision condition. Worst-case: an operator's freshest backup is the one pruned.

**Fix (small, safe):** `snapshot()` must guarantee its own output is never rotated out.
Pass the new backup path into `rotate_backups()` and exclude it from deletion candidates
(it's the freshest by definition, independent of mtime). Secondary hardening: tiebreak the
sort by filename so ordering is deterministic regardless of FS granularity.

```rust
// snapshot(): rotate_backups(path, fname, &backup);
// rotate_backups(): skip the just-written path, and sort_by_key with a filename tiebreak
baks.retain(|(_, p)| p != just_written);
baks.sort_by(|a, b| b.0.cmp(&a.0).then(b.1.cmp(&a.1)));
```
